# Mixer

> Split out of `CLAUDE.md` to keep it under the size limit. Cross-references like "see X" name a section either in `CLAUDE.md` or in another `docs/*.md` file.


`Mixer.svelte` (`src/lib/components/mixer/`) is a draggable floating window (`id="mixer"`, same `FloatingWindow` chrome as Playlist/ChannelRack/PianoRoll) opened from the Toolbar's Mixer button, which uses the same 3-state taskbar semantics as the other three panel buttons (see "Floating windows"). Three columns: a wider Master strip (left) | divider | a horizontally-scrolling row of numbered channel strips (`+` at the end adds a new one, center) | divider | `MixerFxRack.svelte`, a fixed-width FX panel (right) — no cable patchbay anymore (see "History" below for what this replaced). **Real audio routing** — unlike most of the rest of this app's session-only UI state, mixer volume/pan/mute/solo/routing genuinely affect playback via `audioEngine.ts`'s per-track Web Audio graph (see "Real audio graph" below). `mixerStore.svelte.ts` itself is still ephemeral (not wired into `projectSerializer.ts`/undo, same treatment as `windowFocusStore`) — routing/mute/solo choices are lost on reload, which is a bigger tradeoff now that they have real audible consequences than when the Mixer was purely cosmetic; worth reconsidering.

- **Data model** (`mixerStore.svelte.ts`) — `MASTER_TRACK_ID = 0`. `master: MasterChannelData` (`id`, `volume`, `insertSlots`) and `channels: MixerChannelData[]` (`id`, `name` — user-editable, see "Naming & renaming" below — `volume` 0..2 matching `ChannelData.volume`'s convention, `pan` 0..1 matching `ChannelData.pan`'s convention, `muted`, `soloed`, `routeTo: number[]` — every track this channel fans out to, default `[MASTER_TRACK_ID]` — `insertSlots`). Starts with 10 channels. `addChannel()`/`removeChannel(id)` (also drops the removed id from every other channel's `routeTo`, falling back to `[MASTER_TRACK_ID]` if that leaves one with no routes at all, so nothing goes silently unrouted).
- **Selecting a strip** (`selectedChannelId`, `selectedEntity`) — one strip is always "active" (`mixerStore.selectedChannelId`, defaults to the first channel), driving two things at once: the click-to-route UI below, and which strip's insert-slot chain `MixerFxRack.svelte` shows (via `mixerStore.selectedEntity`, which — unlike the routing-only `selectedChannel` getter — resolves to Master's own data when Master is selected). **Master is selectable** (clicking it highlights it and shows its FX chain), it just never gets a routing arrow — it has nowhere to output to, so it can only ever be a routing *target* for other channels' dots, never the active side of a route. The whole strip (`MixerChannelStrip.svelte`'s outer div, both variants) selects on click; individual controls inside it (dots, the remove button, the rename input) `stopPropagation()` so interacting with them doesn't also reselect or fight the strip's own click handler.
- **Click-to-route** (`routingArmed`, `MixerRoutePoint.svelte`) — the active strip shows an arrow at the bottom instead of a routing dot (channel variant only — Master never renders one); every other strip (channels + Master) shows a dot reflecting whether the active channel currently routes into it (green = routed, gray = not; always gray when Master is the active selection, since `mixerStore.selectedChannel` — scoped to `channels` only — naturally returns `undefined` for Master). Clicking the arrow toggles `routingArmed`; while armed, clicking another strip's dot calls `mixerStore.toggleRoute(selectedChannelId, thatId)` (adds the edge if absent, removes it if present) and *stays* armed, so several targets — including sidechain sends — can be wired up in one go without re-clicking the arrow each time. Selecting a different strip disarms routing mode; `MixerRoutePoint.svelte`'s click handler always `stopPropagation()`s so a dot/arrow click never also re-selects the strip it's sitting on.
  - **Cycle prevention** — `mixerStore`'s private `canRoute(fromId, targetId)` walks forward from `targetId` through existing `.routeTo` edges (a general graph now, not a single chain, since routing fans out); if `fromId` is ever reached, the new edge would loop back on itself and `toggleRoute()` refuses to add it (removing an edge is always allowed).
- **Naming & renaming** — a channel's default `name` ("Channel N") is assigned from its *position in the current list* (`this.channels.length + 1` at creation, inside `makeChannel()`), not from its permanent unique `id` — so deleting every channel and adding a new one names it "Channel 1" again rather than continuing to climb through however high the internal id counter had already reached. `id` itself stays a permanent, never-reused counter (`nextChannelId`) — it's the join key `routeTo` and `ChannelData.mixerTrack` actually use, completely decoupled from the display name. Double-clicking a channel's label (not Master's, which stays fixed "MASTER") swaps it for a text input — Enter or blur commits (empty input is ignored, keeping the old name), Escape cancels via a `renameCancelled` guard flag (needed because removing a focused input from the DOM on Escape can still dispatch a trailing `blur` event, which would otherwise re-commit the just-discarded edit), and the input is focused/selected on open the same way `NewProjectModal`'s name field focuses on open. This exact widget is implemented **twice** — once inline in `MixerChannelStrip.svelte` (`renaming`/`nameDraft`/`renameCancelled` local state), once in `MixerFxRack.svelte`'s title bar (same state shape, operating on `mixerStore.selectedEntity` instead of the strip's own `data`) — so a channel can be renamed either from its strip or from the FX rack while it's selected; both write the same `MixerChannelData.name` field, so they can never disagree. Deliberately not factored into one shared component: the two contexts style the label completely differently (a centered strip label vs. a title-bar suffix), and the logic itself is short enough that duplicating it beats forcing a shared component to accept style overrides for two genuinely different looks. The FX rack's version has one extra wrinkle: an `$effect` that resets `renaming = false` whenever `mixerStore.selectedEntity` changes, since (unlike the strip, which is permanently bound to one channel) the FX rack's rename target can be swapped out from under it by selecting a different strip — in practice a blur-before-click already commits before selection changes, but the effect is cheap insurance against a future selection path that skips a DOM blur.
- **Mute/solo** (`MixerMuteSolo.svelte`) — standard multi-solo mixer semantics: `mixerStore.anySoloed` is true if any channel is soloed; `mixerStore.isAudible(channel)` is `!muted && (!anySoloed || soloed)` — an explicit mute always wins regardless of solo. Master is never mutable/soloable. Visually, mute reuses `ChannelRow`'s `.mute-dot` circle idiom exactly (lit = unmuted); solo is a same-size square right next to it (shape, not a second color, distinguishes them — the app only has one accent color token).
- **Strips stretch to the Mixer window's full height** — `.mixer-body`/`.channels-scroll` both use `align-items: stretch` (not `center`), so every strip (Master and channels alike) is as tall as the window allows, and stays that way across resizes rather than sitting at a fixed pixel height with dead space below (or, on a short window, overflowing/getting clipped) — this used to be the actual cause of the Mixer "scaling wrong" on resize. Getting there needs more than CSS alone: `Slider`'s `height` prop isn't just cosmetic (its drag-sensitivity math divides by it), so the fader/meter's pixel size has to be *measured*, not just flex-grown. `MixerChannelStrip.svelte` wraps its non-fader content into two blocks — `.strip-top` (label/rename + remove button + pan dial) above the fader, `.strip-bottom` (mute/solo + the route point) below it — and reads their heights plus the strip's own via three `bind:clientHeight`s (Svelte's built-in ResizeObserver-backed binding, no manual `ResizeObserver` needed). `faderHeight = stripHeight - padding - topHeight - bottomHeight - gaps` (floored at 40px) is then passed as the actual `height` prop to both `PeakMeterVertical` and `Slider`, so they always exactly fill whatever's left in the column.
- **FX rack** (`MixerFxRack.svelte`, right column) — a fixed-width (190px) panel, structurally the same shape as the old shared filter-rack sidebar it replaced, except it's no longer shared: it shows `mixerStore.selectedEntity`'s own `insertSlots` (`MixerInsertSlots.svelte`/`MixerInsertSlot.svelte`, one index + bypass-toggle row each), so it's per-strip and switches automatically as selection moves between channels and Master. Individual channel strips no longer render their own insert-slot list inline — that space was reclaimed once FX moved here. **UI-only placeholders** — there's no plugin/DSP system in this app, so a slot's `enabled` toggle has no audio effect. An unselected state (only reachable if `selectedChannelId` is `null`, i.e. every channel has been deleted) shows an empty-state message instead of a slot list.
- **Real audio graph** (`audioEngine.ts`) — every mixer track (channels + an implicit Master) gets a persistent `TrackChain` (`input` gain → `pan` → `mute` gain, `mute` fanning out in parallel to an `analyser` tap and to however many downstream targets `routeTo` currently lists), created lazily via `ensureTrackChain(trackId)` and kept alive for the session (not per-note). `buildCtx()` inserts a `masterVolumeGain` node upstream of the existing `masterOut` `DynamicsCompressor` — every chain routed (directly or transitively) to Master converges there, and the Mixer's Master fader (`setMasterVolume()`) controls it; `comp`'s own downstream wiring (destination + the toolbar's analyser taps) is unchanged. `setTrackVolume()`/`setTrackPan()`/`setTrackAudible()` write directly to the live nodes' `AudioParam`s (no ramping, matches the instant-assignment convention used elsewhere for UI-driven params). Routing is genuinely multi-target — Web Audio natively supports one node's output fanning out to many destinations — so there's no single "re-point this edge" call: `connectTrackRoute(trackId, targetTrackId)` adds one fan-out edge (`chain.mute.connect(target)`), `disconnectTrackRoute(trackId, targetTrackId)` removes exactly one (`chain.mute.disconnect(target)`, Web Audio's selective-disconnect overload — the shared `analyser` tap, a separate connection, is untouched either way). A triggered sample resolves its destination via `resolveDestination(mixerTrack)`, reading `ChannelData.mixerTrack` (join key, previously dead — now the thing that actually matters): `MASTER_TRACK_ID` or an unmatched id falls straight to Master (matching this app's pre-mixer implicit behavior), otherwise the matching track chain's `input`. `mixerTrack` is threaded through `triggerPitched`/`scheduleHit`/`playSample`/`previewNote` alongside the existing `vol`/`pan` parameters.
- **Bridge from store to audio graph** (`mixerAudio.svelte.ts`) — a plain module singleton following the exact `playbackStore`/`historyStore` `startWatching()`/`stopWatching()` + standalone `$effect.root()` convention (required since a bare `$effect` outside a component has no parent effect context). One `$effect` per concern (chain lifecycle, volume, pan, audibility, routing, master volume) rather than one giant effect, so an unrelated field's change doesn't force re-walking every track. The audibility effect re-runs on *any* channel's mute/solo change, since audibility is a function of the whole channel set (`anySoloed`), not just the one channel being written.
  - **Routing is diffed, not replayed wholesale** — since `routeTo` is now an array and Web Audio has no bulk "these are the only edges now" call, the bridge keeps a `Map<channelId, Set<targetId>>` (`lastRoutes`) of each channel's most-recently-applied edge set; the routing effect compares each channel's current `routeTo` against it and only calls `connectTrackRoute`/`disconnectTrackRoute` for the edges that actually changed.
  - **Removing a channel tears down both directions** — the chain-lifecycle effect detects an id that's disappeared from `mixerStore.channels` and, before calling `removeTrackChain(id)`, first walks every *other* still-live channel's entry in `lastRoutes` and calls `disconnectTrackRoute(otherId, id)` for any that still point at it. This matters because `AudioNode.disconnect()` only ever removes a node's own *outgoing* edges — the now-gone channel's own `removeTrackChain()` teardown cannot reach back and sever another channel's still-live outgoing connection *into* it, so skipping this step would leak a permanently-dangling Web Audio edge. It's safe to run unconditionally even if the separate routing-diff effect already handled a given edge via `mixerStore.removeChannel()`'s own `routeTo` fixup — both paths go through the same `lastRoutes` map and `disconnectTrackRoute()` no-ops once its target chain is already gone.
  - Started/stopped from `+page.svelte`'s `openProject`/`exitProject`, alongside `historyStore`/`playback`.
- **Peak meters** — `PeakMeterVertical.svelte` is a real meter now (same dB-scaling/attack-release/color algorithm as the toolbar's `PeakMeter.svelte`, shared via `meterMath.ts`), resolving its `AnalyserNode`(s) from `audioEngine` fresh every rAF frame by `trackId` rather than a static prop, so it self-heals if the track's chain is created slightly after the meter mounts. Channels get a single mono tap (`getTrackAnalyser(id)`, tapped post-mute so a muted/soloed-out channel visibly reads zero); Master keeps the existing true stereo pair (`getStereoAnalysers()`).

## History

This replaced an earlier cable-patchbay design (`JackPort`/`MixerCables`/`cableGeometry.ts`, a visual side-chain routing system with draggable bezier cables between IN/OUT jacks) and a single shared 10-slot `FilterSlot` sidebar rack unrelated to any specific channel. Neither had any audio-engine wiring behind them. That was itself briefly replaced with a single-target "route to track N" `ScrollField` per channel — too limited for real sidechain use (a channel could only ever feed one bus at a time) — before landing on the current click-to-route model: `routeTo` became multi-target, and the ScrollField gave way to the select-a-channel/arrow/dot gesture described above.

The SVG/cable-drag-freeze lesson from that earlier design (raw `mousemove` unthrottled into a synchronous `getBoundingClientRect()`-driven derivation caused a WebKitGTK layout thrash) doesn't apply here — there's no drag-driven geometry recompute left in the Mixer now that routing is a plain numeric field instead of a pointer gesture.
