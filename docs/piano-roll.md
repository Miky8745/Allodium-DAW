# Piano Roll

> Split out of `CLAUDE.md` to keep it under the size limit. Cross-references like "see X" name a section either in `CLAUDE.md` or in another `docs/*.md` file.


`PianoRoll.svelte` is a draggable floating window (`position: fixed`, same header-drag chrome as `ChannelRack.svelte`) that sits outside the toolbar/left/workspace grid, like `ChannelRack` — it is not subject to the "never place controls in left/workspace" rule since it's an overlay window, not part of either fixed zone.

- **Opening it** — double-click a channel's sample-name box in `ChannelRack`/`ChannelRow` (works even on an empty "Drop sample" channel — notes are channel-scoped, not sample-scoped). It can also be opened from the Toolbar with no channel selected: an `$effect` in `PianoRoll.svelte` selects the first channel whenever the window is shown with no valid selection (also covers deleting the selected channel while it's open). If there are no channels at all it stays unmounted (`{#if channel}`). This sets `channelStore.selectedChannelId` and flips `showPianoRoll` (owned by `+page.svelte`, same as `showChannelRack`). The window always shows/edits `channelStore.selectedChannel`; switching the selected channel while it's open re-targets it live.
- **Coordinate system** — `pianoroll/pitch.ts` is the single source of truth for pixel math: `stepToX`/`xToStep` (16th-note steps, `stepW()` px each) and `pitchToY`/`yToPitch` (semitones, `keyH()` px each, high pitches at the top). Y is always integer-snapped (no fractional pitch concept anywhere in the app). X snaps to whole steps via `xToStep` by default; holding **Shift** during a create/resize/move drag in `NoteGrid.svelte` switches to `xToStepFree` (unsnapped, fractional steps) for pixel-precise length/position — see "Tools" below. A note's `start`/`length` (`types.ts`) can therefore be fractional; `audioEngine.tick()` matches on `Math.floor(note.start)` against the scheduled step and adds a sub-step time offset so a fractionally-positioned note still plays at the right moment instead of never matching an integer step.
- **Zoom** — `pianoRollZoom.svelte.ts`'s singleton `zoom` multiplier (default 1.75x, clamped 0.5x–4x) scales `stepW()`/`keyH()` (and everything derived from them: `gridTotalH()`, note/grid/ruler/velocity-lane sizing) throughout `NoteGrid`/`PianoKeys`/`PianoRollRuler`/`VelocityLane`. `NoteGrid.svelte`'s `.grid-viewport` has an `onwheel` handler that zooms on Ctrl/Cmd+scroll (`e.preventDefault()`'d to block the webview's native page-zoom; plain scroll passes through untouched), and its `handleKeydown` (`svelte:window`, scoped to whenever the Piano Roll is mounted) adds Ctrl/Cmd+`=`/Ctrl/Cmd+`-` for the same zoom in/out, guarded against typing targets the same way `ProjectShortcuts.svelte` guards its own shortcuts. Both paths funnel through `reanchorZoom(anchorX, anchorY, zoomIn)`, which reads `viewportEl.scrollLeft/scrollTop` before changing `pianoRollZoom.zoom`, `await tick()`s for the resized `grid-content` to land in the DOM, then rescales scroll position by the zoom ratio around the same anchor point (cursor position for wheel, viewport center for keyboard) — this is what keeps the same musical content under the cursor/center instead of the view jumping on every zoom step. `MiniNoteRoll.svelte`'s `fit="steps"` mode (the Channel Rack's per-channel preview) deliberately uses `BASE_STEP_W` instead of `stepW()` so its thumbnail scale doesn't change when the Piano Roll is zoomed.
- **Scroll sync without extra scrollbars** — `NoteGrid.svelte`'s viewport is the *only* element with native `overflow: auto`; it reports `scrollLeft`/`scrollTop` up via `onScroll`. `PianoKeys` (Y) and `PianoRollRuler`/`VelocityLane` (X) are `overflow: hidden` and just apply `transform: translate(-scroll…px)` to their content — no bound scroll containers or `$effect`-driven `scrollTop` assignments needed. All three viewport elements (`.grid-viewport`, `.keys-viewport`, `.ruler-viewport`) need an explicit `height: 100%` — without it a block element's `height: auto` sizes to its (huge, 128-pitch) content instead of the CSS-grid-stretched parent, so `overflow: auto`/`hidden` never actually clips anything and there's nothing to scroll.
- **Auto-extend** — `PianoRoll.svelte` runs an `$effect` that checks every channel's notes on each change; if any note reaches into the pattern's current last bar, `channelStore.patternLength` grows by one more bar (`barLength`). This is what lets users keep drawing notes indefinitely instead of hitting the end of the pattern — there's no manual "extend" action.
- **Piano key look** (`PianoKeys.svelte`) — rows are semitone-height (`keyH()`) white bands (needed so they line up 1:1 with `NoteGrid` rows); a black key is rendered as a shorter/narrower absolutely-positioned `.black-key` overlay (`width: 62%`, `top/bottom: 2px` inset) rather than a full-row black background, so it visually reads as a real black key sitting on top of/between white keys instead of a same-size alternating stripe.
- **Key highlight while dragging a note** — `NoteGrid.svelte` derives `highlightPitches: Set<number>` from its own live `drawDrag`/`moveDrag` state (both `$state`, not plain `let`, specifically so this derivation reacts) and reports it up via an `onDragPitchesChange` callback prop (only when the set's *contents* actually change, via a `setsEqual` guard — `$derived.by` otherwise produces a new `Set` reference on every pointermove tick even when nothing visibly changed, which would force a needless 128-row re-render). `PianoRoll.svelte` holds it as `$state` and passes it to `PianoKeys` as `highlightPitches`. Right-click delete-drag does not highlight — only create/resize/move gestures do. Rendering rule in `PianoKeys.svelte`: plain white keys and C rows highlight their whole `.key-row` background orange (`--pr-key-highlight`, `#ff9c33` fallback); black-key rows (including C#) highlight only the nested `.black-key` div, never the row background; a highlighted C row *also* tints the grey bottom half of the C# row directly above it (`.key-row--csharp-below-highlighted`, keyed off `highlightPitches.has(p - 1)` on the C# row) so the C key's grey-sliver illusion into the C# row (see "Piano key look" above) doesn't visually break when only the C row's own highlight is active. The `.black-key--highlighted` rule uses a compound selector (`.black-key.black-key--highlighted`) rather than relying on CSS source order, since it needs to reliably beat the base `.black-key` background regardless of declaration order.
- **Tools** (`PianoRollHeader.svelte`, `tool: PianoRollTool = 'draw' | 'delete' | 'marquee'`, type exported from its `<script module>`, bindable) — classic click-to-place model, no multi-row "paint" mode. There is no separate Select tool any more:
  - **Draw**: click on empty space clears the selection and places one note at `lastLength` in `noteDefaults.props.color` (`lastLength` is a `NoteGrid`-local `let`, default 8 steps/2 beats). Keeping the button down and dragging from that same click **moves** the new note (position + pitch, through the same `moveDrag` path as existing notes, via `startMoveDrag(..., ids=[note.id])` since it isn't selected) — it no longer resizes; length only changes by grabbing a note's right edge. **Clicking a note selects it** (plain = select just it; Ctrl toggles, Shift adds — modifiers only for multi-select) and `adoptTemplate()`s it: its length → `lastLength`, its color → `noteDefaults.props.color`, so the next placed note copies both. Dragging a note's body moves the whole selection (`moveDrag`); a plain click without moving on a note inside a multi-selection narrows the selection to it (`collapseOnClick`). Dragging a note's last ~6px resizes just it. Ctrl/Shift+drag on empty space marquee-selects. Snapping is on by default; holding **Shift** *during* a drag frees the X axis to fractional steps (Shift held *at mousedown* means "add to selection").
  - **Marquee (drag select)**: every drag draws a selection box, even one starting on a note (never moves notes). Plain = replace, Shift = add, Ctrl = toggle (same semantics as `ChannelRack.handleSelect`). A click without dragging selects the note under the cursor (a zero-size box overlaps it — `noteOverlapsRect` uses `<=` on the min edges for this) and adopts it as the template, or clears on empty space.
  - **Delete**: left click deletes the note under the cursor, dragging deletes every note passed over. The right button does the same in every tool (`deleteButtons` remembers which button's `e.buttons` bit drives the gesture). Deleted notes play the shared deletion effect (see "Deletion effect" below) on the keyed `{#each channel.notes as note (note.id)}` block, wrapped in `{#key channel.id}` so switching channels reads as a remount.
  - **Keyboard / selection look** — Delete/Backspace removes selected notes; **Delete with nothing selected clears every note** of the open channel (in the current pattern) — Delete only, not Backspace, and only while the Piano Roll is frontmost; undoable via the normal history watcher; Ctrl/Cmd+C/V copies and pastes right after the copied block's end (clamped to `patternLength`); Ctrl/Cmd+A selects all (only while the Piano Roll is frontmost); Escape clears. Selected notes get a white rim + glow + diagonal stripes and every unselected note dims to 40% while a selection exists (a fill-color swap can't stay distinguishable across 15 user-editable colors).
  - **Audio preview** — `audioEngine.previewNote(channel, pitch)` (public; internally reuses the private `triggerPitched`/`ensureCtx` scheduler plumbing with an immediate `playTime` and a short fixed `PREVIEW_DURATION`/`PREVIEW_VELOCITY`) fires once whenever a note is placed or an existing note is clicked, and again whenever a note being moved crosses into a different pitch row (tracked via `lastPreviewPitch` on the drag state) — not on every pointermove tick, and not during a pure length-resize (pitch doesn't change).
- **Note properties & slide notes** — every `Note` carries `velocity`, `pan` (offset on the channel pan, 0.5 = none), `release` (0..1; 0.5 = the old fixed 50ms `RELEASE`, higher rings past the note end up to 2s, see `releaseSeconds()`), `modX`/`modY` (per-note lowpass cutoff 50Hz–20kHz / resonance, the usual sampler mapping; no filter node at the defaults 1/0), `finePitch` (cents ±1200), `color` (palette index 0–14, default lime) and `slide`. `NotePropertiesPanel` edits the **selected notes** when there are any, otherwise `noteDefaults` (what `NoteGrid.createNote()` copies). If the selected notes disagree on a property it's *mixed*: the control shows that property's default, dimmed, labelled MIXED (palette: no swatch highlighted; slide: dashed), and nothing is written until the user actually drags/clicks it — Dial's function binding only calls the setter on user input. Notes render in their palette color; slide notes are translucent with a ramp glyph. `previewNote(ch, pitch, props)` applies a note's pan/fine pitch/filter/release. Old saves/history lack these fields — `channelStore.importState()` runs `normalizeNote()`; Rust `NoteData` has serde defaults (and `start`/`length` are now `f64` — they were `u32`, which broke saving Shift-free fractional notes).
  - **Slides** — a slide note never sounds and never goes out as MIDI. When it starts, every note **of the same channel and same color** that's playing at that moment (`start ≤ t < note end`, release tail excluded) glides to the slide note's pitch (incl. its fine pitch — an *absolute* target, so chords need one color per voice) over the slide note's length, then stays there; consecutive slides chain from wherever the previous left off (a slide arriving mid-glide truncates it). `scheduleChannelStep` calls `slides.addSlide()`; `playSample` calls `slides.registerVoice()` for every piano-roll voice. Because voices register asynchronously (after sample load) and a slide in the same step may be scheduled before its target, whichever arrives second applies the bend. `audioEngine.stop()` clears pending slides. Unrelated to live MIDI pitch bend (`setLiveVoiceBend`).
- **Deletion effect** (`src/lib/deleteFx.ts`, Piano Roll notes + Playlist placements) — the deleted element fades out over 240ms while a 2px red outline with the same size/`border-radius` scales up from its center (1→1.07) and fades over 750ms. `deleteOut` is an `out:` transition that spawns the ring as a plain DOM node in the element's `offsetParent` (Web Animations API, self-removing — it has to outlive the element). It only plays for elements **marked** via `markDeleted(key)` right before removal, matched against the element's `data-del-key` (`note:<channelId>:<noteId>`, `placement:<id>`); anything else leaving its list (moving a placement to another track, pattern switch, undo) disappears instantly. Placements need `out:deleteOut|global` because their blocks sit inside `{#if}`s within the each item. New deletion paths must call `markDeleted` to get the effect.
- **Velocity indicator on notes** — each note in `NoteGrid.svelte` carries a `.note-velocity` bar along its bottom edge: 3px tall, darker accent shade, width = `note.velocity` × the note's own width (velocity 1 spans the full note). Purely a display of the same 0–1 value the velocity lane edits.
- **Velocity lane** — one bar per note (`VelocityLane.svelte`), height ∝ `note.velocity` (0–1). Drag vertically to set; dragging across several bars in one gesture sets each as the pointer passes over it (same mousedown-then-pointerenter-while-buttons-held pattern as the step paint gesture).
- **`MiniNoteRoll.svelte` (`pianoroll/`)** — the shared note-thumbnail renderer used both by the Channel Rack's mini piano-roll preview and the Piano Roll's overview panel (below). Props: `notes`, `patternLength`, `activeStep`, `rowHeight`, `fit: 'steps' | 'stretch'`. Vertical axis is always squashed to `rowHeight` by auto-fitting to *this channel's own* min/max note pitch (not the full 0–127 keyboard — 128 semitones in a ~28px row would make notes sub-pixel), with a minimum bar height and a `span` clamped to 1 so a single shared pitch centers rather than divides by zero. `fit="steps"` (the Channel Rack's mode) lays out in real pixels via `STEP_W`/`stepToX`/`patternWidth` from `pianoroll/pitch.ts`, so it's pixel-accurate against the real grid and lines up with neighboring step rows. `fit="stretch"` (the overview panel's mode) instead expresses note/playhead position as percentages of `patternLength`, so the *whole* pattern condenses to fit whatever width the panel has, regardless of pixels-per-step.
- **Mini piano-roll preview in the Channel Rack** — `ChannelRow.svelte`'s `.steps` area shows the step-sequencer buttons only when `channel.notes` is empty; otherwise it renders `<MiniNoteRoll fit="steps">` instead, since a note-based channel's step buttons don't reflect what's actually scheduled (`audioEngine` plays *only* from `notes` when any exist). Editing still only happens via the floating Piano Roll window (double-click the sample name) — the mini-roll has no pointer handlers.
- **Overview/minimap panel** (`PianoRollOverview.svelte`) — a full-width strip above the Piano Roll's main grid, toggled by the "Piano roll overview" button in the Channel Rack header (`showPianoRollOverview`, lifted into `+page.svelte` and passed to both `ChannelRack` and `PianoRoll` the same way `showPianoRoll`/`showChannelRack` are). Renders `<MiniNoteRoll fit="stretch">` for the whole pattern, with a lighter-gray overlay rectangle showing the fraction of the pattern currently visible in `NoteGrid`'s viewport — computed purely from ratios against `patternWidth(patternLength)` (`scrollLeft`/`viewportWidth`), no DOM measurement of the mini-roll itself needed. Click or click-drag anywhere in the strip seeks: `NoteGrid.svelte` exposes an `export function scrollTo(x, y)` (set via `bind:this`) that a parent can call to scroll it from outside — setting `scrollLeft`/`scrollTop` directly fires the existing native `onscroll` handler, so the overlay's position self-corrects from the real post-clamp value with no extra plumbing. `NoteGrid`'s viewport width is tracked reactively (a `ResizeObserver` on the viewport element, reported via an `onViewportResize` callback prop) since it's otherwise only read once, non-reactively, at mount.
- **Piano Roll's own play button** (`PianoRollHeader.svelte`) — plays *only* the currently-open channel by setting `playback.soloChannelId` before starting (see "Audio / playback" above); pressing it again just stops. Reuses the exact `hdr-btn hdr-tgl` chrome/SVGs as `ChannelRack`'s play button.
- **Continuous playhead line** (`NoteGrid.svelte`) — a separate, thin 1px line (distinct from the existing discrete `.playhead` step-highlight band, which stays for cell-alignment purposes) driven by `playback.currentStepFraction` rather than the floored `currentStep`/`activeStep`, so it moves smoothly instead of snapping per 16th-note. Only rendered while `playback.isPlaying` (`PianoRoll.svelte` passes `-1` otherwise, the same sentinel convention as `activeStep`).
- **Playhead is wrapped to the open channel's own loop length, not shown as the raw absolute position** — `playback.currentStep`/`currentStepFraction` are absolute, unwrapped positions within `channelStore.activeLength` (see "Per-channel independent looping" above). `PianoRoll.svelte` computes its own `chLoopLength = channelLoopLength(channel, activeLength, barLength)` (same helper `audioEngine.tick()` uses) and derives `wrappedStep`/`wrappedStepFraction` (`currentStep % chLoopLength`, guarded by the `-1` idle/not-playing sentinel) fed to `NoteGrid`, `PianoRollRuler`, and `PianoRollOverview` alike, instead of the raw store values directly. Without this, a channel whose content loops shorter than the shared active region would show a playhead sweeping across empty canvas for most of the region instead of cycling back over its own notes — reading as if it were tracking a different (longer) channel's timing rather than its own.
