# Playlist

> Split out of `CLAUDE.md` to keep it under the size limit. Cross-references like "see X" name a section either in `CLAUDE.md` or in another `docs/*.md` file.


`Playlist.svelte` docks a fixed-width patterns panel on the **left** of the timeline (inside `.playlist-body`, a sibling of the scrollable `.playlist` grid — not part of the toolbar/left/workspace zone rule, since this is internal to the Playlist floating window). Each of the 8 fixed timeline tracks (`Track { id, name, color }`, local `$state` in `Playlist.svelte`, not persisted — not a store, since there's no per-track behavior yet beyond visual lanes) is rendered by `playlist/PlaylistTrackRow.svelte`.

- **Patterns panel data** — `patternStore.svelte.ts` (singleton) holds the list of `PatternData` (`id`, `name`, `color`, `lengthBeats`) and `selectedPatternId`. The panel and the Toolbar's pattern dropdown both read/write this same store, so selecting a pattern in either place stays in sync. `+` at the bottom of the panel first opens `playlist/NewPatternModal.svelte` (portalled, z-index 9000): a name prompt seeded with — and pre-selecting — `patternStore.nextPatternName` (what would be auto-assigned), so Enter/OK straight away accepts it; an emptied field falls back to it; Escape/Cancel/backdrop creates nothing. Only then does it call `patternStore.addPattern(name)`.
- **Renaming, recoloring & deleting patterns** (`playlist/PatternsPanel.svelte` → `PatternCard.svelte`/`PatternContextMenu.svelte`) — clicking a card only makes it the **active** pattern (`patternStore.selectedPatternId`, colored border — what gets drawn/edited); the panel has no selection of its own. Clicks/double-clicks/right-clicks on a card's length `ScrollField` (`.sf-wrap`) are ignored by the card.
  - **Rename** — double-click a card, or right-click › "Rename pattern": the name swaps for an input; Enter/blur commits (empty keeps the old name), Escape cancels (`cancelled` guard against the trailing blur, same trap as `MixerChannelStrip`). The input's keydown `stopPropagation()`s so Delete/Space don't hit window shortcuts.
  - **Recolor / Recolor randomly** — same two options as ChannelRow's menu (`ColorWheel` live-writing `pattern.color`, or `randomColorfulHex()`).
  - **Delete — right-click › "Delete pattern" only** (deliberately no Delete key in the panel: the Delete key removes *placed blocks* selected on the timeline, see "Tools & block selection"). Goes through `patternActions.ts`'s `deletePatterns()`: removes that pattern's placements, then `patternStore.removePatterns()` — if the active pattern is removed the next surviving one (else the previous) becomes active *first* (via the public setter, so `switchPattern` stashes live content normally), deleting every pattern leaves one fresh blank pattern (the app always needs an active one), and `channelStore.removePatternContent(id)` drops each removed pattern's stashed step/note content. Cards and placements get the deletion effect (`pattern:{id}` / `placement:{id}` keys). One undo step.
- **Tools & block selection** (`playlist/playlistEditor.svelte.ts`, header buttons via `EditToolButtons`) — the Piano Roll's three tools applied to placed blocks; `editor.tool` is ephemeral (defaults to Draw). Lane/track-row cursor follows the tool (brush / eraser / crosshair, set in `PlaylistTrackRow` from its `tool` prop).
  - **Draw** — clicking empty lane space clears the selection and places the active pattern (see "Placing a pattern" below). Clicking a block adopts its pattern as the active one and selects it (plain = just it; Shift adds); dragging moves the whole selection; a plain click on a block inside a multi-selection without moving narrows the selection to it (`collapseTo`, like the Piano Roll's `collapseOnClick`). Shift+drag on empty lane space marquee-selects. **Ctrl+drag is the Drag-select tool's drag in every tool** (Draw/Delete, on blocks too — `onLanePointerDown`/`onPlacementPointerDown` route Ctrl/Cmd to `#startMarquee`); there is no Ctrl-toggle selection anymore.
  - **Delete** — left click/drag erases blocks (same drag-delete as the right button).
  - **Drag select** — every drag (even one starting on a block) draws a box: plain = replace, Shift = add; hit-tested live against the rendered `[data-placement-id]` elements' rects (a zero-size click box hits the block under it, which is also adopted). The box (`.marquee`) is stored in grid-local px and drawn inside `.grid`.
  - **Right button = delete / drag-delete in every tool**; `#deleteBit` remembers which `e.buttons` bit drives the gesture.
  - **Keyboard** (`Playlist.svelte`'s `handleKeydown`, only while shown + `isFrontmost('playlist')`, ignoring typing targets): Delete/Backspace removes the selected blocks (`deleteSelected()`, deleteFx on each, one undo step); Ctrl/Cmd+A selects every block; Escape clears; Space plays/pauses. NoteGrid's Delete handling is gated on `isFrontmost('piano-roll')` (both branches) so the two windows' Delete never collide.
  - **Selection look** — selected blocks get a white rim + glow and every other block dims to 50% while a selection exists (same idea as Piano Roll notes). The selection is ephemeral and pruned (`editor.prune()` in an `$effect`) when placements disappear (delete, undo, load).
- **Pattern length** — edited inline per pattern card via a `ScrollField` (`decimals={2}`, `step={0.25}`), so lengths like `4.5` beats are representable (needed for unquantized audio clips such as vocal takes).
- **Placements: patterns and clips** — `Placement` (`types.ts`, held in `placementStore.svelte.ts`, not local component state, so it participates in save/undo) has a `kind: 'pattern' | 'clip'` discriminator with sentinel-valued fields on whichever side is unused, rather than `Option<T>`-style nullable fields: `patternId` (real id when `kind==='pattern'`, `0` when `kind==='clip'`), `samplePath` (real data-relative path when `kind==='clip'`, `''` when `kind==='pattern'`), `lengthBeats` (the clip's own length when `kind==='clip'`, `0` when `kind==='pattern'` — a pattern placement's length always comes from `PatternData.lengthBeats` looked up live instead, not copied at drop time, so resizing a pattern's length in the panel resizes every placed instance of it). This sidesteps quick-xml's documented `Option::None → Some("")` round-trip quirk (see "Sample paths" below) entirely on the Rust side (`project.rs`'s `PlacementXml`) rather than replicating the workaround a second time, and avoids a real risk of a numeric `Option` failing to deserialize at all (an empty tag's content isn't valid number text, unlike the string case).
  - **Placing a pattern = drawing, like the Piano Roll's Draw tool** — clicking an empty spot in a track lane (`PlaylistTrackRow`'s row `onpointerdown` → `editor.onLanePointerDown`, Draw tool only, ignored on the sticky track panel; placed blocks `stopPropagation`) calls `placementStore.addPattern(patternStore.selectedPattern, trackId, beat)` in the clicked beat cell (`Math.floor`; Shift/Ctrl at mousedown means marquee-select instead), then starts the live move on it so keeping the button down moves the new block. If the clicked cell can't fit the pattern it's placed flush against the neighbour instead, but never more than its own length from the click (else nothing is placed). The pattern drawn is `patternStore.selectedPatternId` — set by clicking a card in the patterns panel, the Toolbar's pattern dropdown, or clicking an already-placed pattern block (adopts it, like the Piano Roll adopting a clicked note). Pattern cards no longer drag. In the Draw tool lanes show the brush cursor; track panel and blocks the regular one. **No overlapping blocks on a track** — drawing, moving and clip drops all go through `src/lib/placementLayout.ts`'s `nearestFreeStart()` (candidates: the desired start plus the slots flush against each neighbour's edges; the closest one that fits wins, so a block pushed into another sticks to its side). A clip's start is re-fitted once its real decoded length is known. Pattern lengths can still grow later (content/`ScrollField`) and overlap — not prevented. `pixelsPerBeat` is just `beatWidth` (see "Grid resolution" below).
  - **Grid resolution is one beat per cell, not one bar** — `Playlist.svelte`'s `beatWidth` (`$state`, default 40px) is the pixel width of a single beat-cell; `barCount` (`$state`, default 64) is how many bars' worth of timeline to render, and `beatCount = $derived(barCount * channelStore.beatsPerBar)` is the actual number of cells `PlaylistTrackRow` draws. This means the grid is `beatsPerBar`x finer/wider than a bar-per-cell grid would be at the same per-cell pixel width (4x wider for the default 4/4 signature) — each beat gets its own gridline instead of the whole bar collapsing into a single 40px cell. `PlaylistTrackRow`'s `.beat-cell` shading (`cellBg()`) and the `group-start` border alternate every `channelStore.beatsPerBar` cells, i.e. once per bar; the ruler (`Playlist.svelte`) renders one `.ruler-group` per bar (width `beatsPerBar * beatWidth`, labeled with the bar number), not per fixed 4-bar block like before.
  - **Placing a clip** — dropping a single audio file from `FileExplorer` onto a track (folder drops are a no-op — only single-file drops create clips) calls `placementStore.addClip(samplePath, trackId, startBeat, lengthBeats)` **immediately**, at a `CLIP_FALLBACK_LENGTH_BEATS = 4` placeholder width, then corrects `lengthBeats` via `placementStore.update()` once `audioEngine.loadSample()`'s async decode resolves (`buf.duration / (60 / playback.tempo)`) — so the block appears the instant you let go and snaps to its real width a moment later. `FileExplorer`'s `filedrop` `CustomEvent` carries the drop's client `x`/`y` on its `FileDropDetail` (captured from `FileExplorer`'s own drag-only pointer tracking, at zero extra cost), so `PlaylistTrackRow`'s own `filedragenter`/`filedragleave`/`filedrop` listeners (added on the row alongside its existing `data-track-id`, via `data-sample-drop` — same attribute-presence convention `ChannelRow.svelte` uses) can resolve the drop beat straight from the event. **Do not** reintroduce a second always-on document-wide `pointermove` listener in `Playlist.svelte` to track cursor position for this — an earlier version did exactly that, updating `$state` on every mouse pixel move for as long as the Playlist window was mounted (i.e. most of the session), which is the same raw-unthrottled-`mousemove`-into-reactive-state pattern that once caused a WebKitGTK layout thrash in the old cable-patchbay Mixer (see "History" under "Mixer") — carrying coordinates on the event itself avoids the whole class of bug.
  - **Moving/deleting placements — same model as the Piano Roll's note move** — pressing a block (Draw tool) starts `moveDrag` (no threshold, no ghost) for the whole selection: blocks follow the pointer live, snapped by the pointer's whole-beat delta from where it grabbed (`floor(now) - floor(anchor)`, so blocks keep their offset; Shift during the drag = unsnapped), and the track delta under the pointer (`elementsFromPoint` → `data-track-id`, as an index offset into `tracks`) shifts their tracks; the group is clamped to beat ≥ 0 and the existing tracks. A **single** block resolves through `nearestFreeStart()` (sticks flush to a neighbour); a **multi-block** selection moves rigidly and stops at the last position where `placementLayout.ts`'s `groupFits()` says nothing outside the group overlaps. Window-level `onpointermove`/`onpointerup` in `Playlist.svelte` forward to the editor; moving blocks get `.moving` via `PlaylistTrackRow`'s `movingIds` prop. Right button / Delete tool: deletes the block under the pointer and, while the button stays held, every block passed over (hit-tested with `elementsFromPoint` on `data-placement-id`; eraser cursor; deleteFx on each). A clip placement is only ever *created* via the file-drop gesture.
- **Placement previews** — `playlist/PlaylistPatternPreview.svelte` renders a combined thumbnail of *every* channel in a placed pattern (not just one), reusing `MiniNoteRoll`'s `fit="stretch"` mode (its geometry — `pitchRange`/`barHeight`/`barTop` — is already channel-agnostic, operating on a flat `notes` array with no per-channel awareness, so flattening multiple channels into one array with offset ids, `channelId * 1_000_000 + localId`, is a drop-in reuse). Fetches every channel's content for that pattern via `channelStore.getPatternChannels(patternId, selectedPatternId)` (see "Audio / playback" below). A channel with piano-roll notes contributes them directly, once each (Song mode plays a note channel through once — see "Song mode" below — so the preview doesn't repeat them either); a step-sequencer-only channel (no notes, just `steps[]`) synthesizes one synthetic `Note` per active step on a single **virtual row** — pitch `lowestMelodicPitch - 1` (or `0` if the pattern has no melodic notes), i.e. as if the pattern had a super-deep tone just under its real range, with `length` derived from that channel's own sample's decoded duration converted to 16th-note steps (`buf.duration / (60/bpm/4)`, resolved async via `audioEngine.loadSample()`), then drawn at a quarter of that and capped at 1 step (1-step fallback until resolved) so hits on adjacent steps never merge even with every step filled — short samples still read shorter than long ones, but long ones don't smear across neighbouring steps. Since Song mode loops a step channel to fill the whole block (`channelLoop.ts`'s `channelLoopLength`, same helper `audioEngine` uses, with `loopNotes=false`'s bound), the preview tiles that channel's synthetic notes across every repeat (`for (cycleStart = 0; cycleStart < patternLengthSteps; cycleStart += loopLen)`) rather than only drawing its first cycle — otherwise a short drum loop would visually stop after one bar while still audibly looping for the whole placement. The virtual row is a real row inside `MiniNoteRoll`'s autofit (the range simply grows by one), not a fixed pitch far outside it — a far-off pitch would land outside the thumbnail and be clipped invisible. Steps at/after `loopLen` are skipped (they never play — `audioEngine` wraps the step modulo `loopLen`, e.g. steps 12–15 in 3/4) and each note's length is clamped to the block's end. `playlist/PlaylistClipWaveform.svelte` renders a placed clip's actual waveform instead: a `<canvas>` sized to its container × `devicePixelRatio`, drawing one min/max-per-pixel-bucket vertical line per column from `buf.getChannelData(0)` (mono/first-channel only) — built from scratch, no prior waveform code existed anywhere in the app (`BlackBox.svelte`'s canvas is a fixed-resolution real-time oscilloscope, CSS-stretched, not a per-sample static render). A `ResizeObserver` redraws it if the block's width changes (Playlist zoom).
- **Song overview bar** (`playlist/PlaylistOverview.svelte`) — a strip above the scroller (outside it, in `.timeline-col`, so it never scrolls), same height as the ruler (`RULER_H`, raised from 24 to 36px), with a "Song" corner over the track panel. One lane per track (`laneH = 100% / tracks`), one rounded block per placement in its pattern color (clips `#6c91b1`), lengths from `patternStore.effectiveLengths` exactly like `PlaylistTrackRow`. It maps a *range* of beats onto its width: song end + 2 bars of headroom, grown to include the current view if you've scrolled past that, capped at `beatCount`; the range is frozen during a drag so the mapping can't rescale under the cursor. The lighter `.ov-window` overlay is the visible region (`scrollLeft / beatWidth`, width `(scroller clientWidth - TRACK_PANEL_W) / beatWidth`); dragging it, or clicking elsewhere (centers the window there, then keeps dragging), sets the scroller's `scrollLeft` via `onScrollTo` (pointer capture on the map). `Playlist.svelte` mirrors `scrollLeft`/`clientWidth` from the scroller's own `onscroll`/`bind:clientWidth`.
- **Song-mode playhead** — a thin glowing 1px line (`.playhead-line`, styled identically to the Piano Roll's `NoteGrid.svelte` `.playhead-line`) at beat `playback.currentStepFraction / 4`, drawn in a `.playhead-clip` overlay **outside** the scroller (over `.timeline-col`, clipped to the lanes, `translateX(beat * pixelsPerBeat - scrollLeft)`) — see "Per-frame updates" below for why, shown only while `playback.isPlaying && playback.transportMode === 'song'` — meaningless in pattern mode, where the timeline position has no relationship to what's playing. See "Audio / playback" for how song-mode playback itself works.
- **Per-frame updates must not live inside a scroller, and must use `transform`** — anything that changes every animation frame (playheads, step highlights) inside an `overflow: auto` container made WebKitGTK re-render that scroller *and every floating window stacked over it* each frame. The Song-mode playhead used to be a `left`-positioned child of the Playlist grid: once it travelled under the Piano Roll/Channel Rack/Mixer ("lags after ~4 bars") each frame cost ~40ms — ~25fps and 100ms+ main-thread stalls, past the audio scheduler's look-ahead, so audio glitched too. Measured with `scripts/profile.sh`: one window over the Playlist, Song mode 25–31fps → 61–63fps after moving the playhead to an overlay outside the scroller. `NoteGrid`'s playhead band/line got the same overlay treatment (`.playhead-overlay`, offset by its own `scrollX`), `MiniNoteRoll`'s mini-playhead moved from `left` to `transform`. `will-change`/`contain` on the windows did **not** help (no effective layer isolation in this WebKit), nor did removing shadows/filters. Still open: with 3–4 windows all stacked over the Playlist it drops to ~25–40fps even in pattern mode under Xvfb's software rendering (the Channel Rack's per-step `.step--playing` class changes inside `.rack-list` are a remaining candidate); untested on real GPU compositing.
- **Song start marker** — clicking the ruler sets `playback.seekStep` (steps, snapped to the nearest 16th) and draws `.seek-arrow` there; this works while playing too, in which case the same click also calls `playback.jumpTo(step)` → `audioEngine.seekToStep()` to live-jump the playhead (song mode only). Pressing Play in Song mode begins from the marker: `playbackStore` passes `seekStep` as `audioEngine.startSong()`'s trailing `startStep` arg (which sets `scheduledStep` and back-dates `loopAnchorTime` so the visual playhead agrees). It's read via `untrack()` in the watcher effect so moving the marker mid-song doesn't restart the transport; pattern mode is unaffected. A marker at/after the arrangement's end falls back to 0. **Don't** apply the seek with a separate call right after `start()`/`startSong()` — both are `async` (they `await ensureCtx()`) and reset `scheduledStep` when they resume, which silently clobbers a synchronous seek made just after calling them (this was the original bug).
- **Space = play/pause** — `Playlist.svelte`'s `<svelte:window onkeydown>` calls `playback.togglePlay()` on Space, only while the Playlist is shown and `windowFocus.isFrontmost('playlist')` (the Playlist stays mounted when hidden, and this is a window-level listener, so the focus check keeps it from firing while another floating window is in front); ignored for `input`/`textarea`/`select`/contenteditable targets. Like the Toolbar's Pause button, resuming restarts from the start marker rather than the paused position — there's no real pause/resume-in-place in the engine.
- **Automation clips** — not implemented. A future `kind: 'automation'` would follow the same sentinel-field pattern as `'clip'`.
