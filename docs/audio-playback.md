# Audio / playback

> Split out of `CLAUDE.md` to keep it under the size limit. Cross-references like "see X" name a section either in `CLAUDE.md` or in another `docs/*.md` file.


The sequencer uses the Web Audio API look-ahead scheduler pattern for accurate timing:

- **`src/lib/playbackStore.svelte.ts`** — Svelte 5 class-based shared state and the app's single unified playback clock: `isPlaying`, `tempo` (BPM), `currentStep` (floored, -1 when stopped), `currentStepFraction` (continuous, non-floored — drives the Piano Roll's smooth playhead line), `soloChannelId` (`number | null` — when set, only that channel plays; set only by the Piano Roll's own play button), `transportMode` (`'pattern' | 'song'` — real engine behavior, see "Song mode" below, not just Toolbar PAT/SONG display state), `metronomeOn` (Toolbar's metronome toggle — lives here, not in `Toolbar.svelte`, since `audioEngine.tick()` needs a live getter for it exactly like `tempo`/channels/`barLength`). `startWatching()`/`stopWatching()` (called from `+page.svelte`'s `openProject`/`exitProject`, alongside `historyStore`) open a standalone `$effect.root()` (same reasoning as `historyStore.svelte.ts` — a plain module singleton has no parent effect context) that owns *all* `audioEngine.start()`/`startSong()`/`stop()` orchestration and the `requestAnimationFrame` loop advancing `currentStep`/`currentStepFraction` — this used to live inside `ChannelRack.svelte`, which meant playback silently stopped advancing its visual position if that window was ever closed while playing; now it runs regardless of which windows are open. The `$effect` reads `transportMode` as a dependency, so flipping the Toolbar's PAT/SONG toggle *while playing* immediately restarts the transport in the new mode rather than only taking effect on the next manual play/stop. `restartFromZero()` is called by `patternStore`'s `selectedPatternId` setter on every pattern switch — if playing, it actually restarts the audio loop at step 0 of the new pattern; if stopped, it just resets the idle marker (pattern-mode-only, no song-mode equivalent — there's no "switch active song position" action anywhere in the UI). `Toolbar`, `ChannelRack`, and `PianoRoll` all read/write the singleton `playback` object, so their play buttons stay in sync automatically (shared reactive state, no cross-component events).
- **`src/lib/channelStore.svelte.ts`** — Svelte 5 class-based shared state: `channels` (`ChannelData[]`), `patternLength`, `selectedChannelId` (+ `selectedChannel` getter), `addChannel()`, `removeChannel(id)` (also purges the channel's stashed content from every other pattern and clears `selectedChannelId` if it pointed at the removed channel). `ChannelRack` and `PianoRoll` both read/write this singleton so they operate on the same channel data.
  - **Deleting a channel** — right-click anywhere on a `ChannelRow` except the step buttons (which keep their own right-click-to-erase-step meaning, see "Sequencer paint" further down) opens a small context menu (`ChannelRow.svelte`'s own `contextMenu` state, portalled onto `<body>` the same way `DragTooltip.svelte` is, so it escapes the Channel Rack list's `overflow: auto` clipping) with a single "Delete channel" action that calls `onDelete` → `ChannelRack.handleDelete(id)` → `channelStore.removeChannel(id)`.
  - **Time signature / pattern length** — `beatsPerBar` (numerator, denominator fixed at quarter notes, default 4) and `patternLength` are both getter/setter pairs. `patternLength`'s setter always snaps to the nearest whole multiple of `barLength` (`= beatsPerBar * 4` sixteenth-note steps), so the pattern can never end mid-bar — 4/4 → multiples of 16, 3/4 → multiples of 12, 2/4 → multiples of 8, etc. Setting `beatsPerBar` re-snaps `patternLength` to the same bar *count* under the new bar length. `ChannelRack`'s "TIME SIG"/"LEN" `ScrollField`s bind directly to these accessors.
  - **`getPatternChannels(patternId, selectedPatternId)`** — read-only view of a pattern's channels (shared settings merged with that pattern's own stashed step/note content) without disturbing whichever pattern is actually open, unlike `switchPattern()` (which mutates live state and would visibly disrupt the open Piano Roll/Channel Rack). Takes `selectedPatternId` as an explicit parameter rather than importing `patternStore` (which already imports `channelStore` — importing back would be a needless circular module dependency) — any reactive caller that reads `patternStore.selectedPatternId` to pass in here naturally reruns on every pattern switch, which is what picks up fresh content the moment `switchPattern()` stashes it. Shared by `audioEngine`'s song-mode scheduler and `playlist/PlaylistPatternPreview.svelte` (see "Playlist" above).
- **`src/lib/audioEngine.ts`** — singleton `audioEngine`. `start(getBpm, getChannels, getActiveLength, getBarLength, getMetronomeOn)` takes *getters* (closures), not direct values, so that live BPM/channel/length changes are picked up on each scheduler tick without restarting the engine. Uses `AudioContext.currentTime` for sample-accurate scheduling (`source.start(time)`). 100ms lookahead, 25ms tick interval. `startSong(getBpm, getSongPlacements, getPatternChannels, getSongLength, getBarLength, getMetronomeOn, onSongEnd)` is the song-mode counterpart — see "Song mode" below.
- **Song mode** (`src/lib/songTimeline.svelte.ts`, `audioEngine.ts`) — `transportMode === 'song'` plays the Playlist's actual arrangement instead of looping the selected pattern; `'pattern'` mode is completely unchanged (same `start()`/`getChannels()`/`activeLength` path as always). `songTimeline.svelte.ts`'s `getSongPlacements()` translates `placementStore.placements` into step units (`SongPlacement { kind, trackId, startStep, lengthSteps, patternId?, samplePath? }` — `startBeat × 4`, a clip's from its own `Placement.lengthBeats × 4`). A pattern placement's `lengthSteps` is **not** just `PatternData.lengthBeats × 4` — it's `patternStore.effectiveLengths.get(patternId) × 4`: "as long as the longest channel in the pattern" (the furthest reach of any of that pattern's channels — a note channel's last `note.start + note.length`; a step channel's last active step index — rounded up to a whole bar, via `channelLoop.ts`'s `patternContentLength()`), floored to at least `pattern.lengthBeats × 4` so the patterns-panel `ScrollField` still works as a manual *minimum* (useful for padding out trailing arrangement space) rather than a hard cap — a pattern's own content can never be silently truncated just because its manually-set beats field is shorter than what's actually drawn in it (the default is 4 beats/1 bar, easy to outgrow without noticing). `PlaylistTrackRow.svelte`'s placed-pattern block width reads the exact same `patternStore.effectiveLengths` map, so the block drawn in the Playlist always matches what Song mode will actually schedule. `getSongLengthSteps()` is the max end across all placements (using this same effective `lengthSteps`), rounded up to a whole bar (floored at one bar for an empty arrangement).
  - **`patternStore.effectiveLengths` is memoized (`$derived.by`), not recomputed per read** — both `songTimeline.svelte.ts`'s `placements`/`lengthSteps` and `PlaylistTrackRow.svelte`'s block width read this one shared map instead of each independently re-scanning every channel's content. This matters because `audioEngine.tick()` (the Song-mode scheduler) reads `getSongPlacements()`/`getSongLengthSteps()` via plain closures up to twice per 25ms tick — without memoization that's a full per-placement, per-channel bar-scan 80+ times a second regardless of whether anything changed, which is what made pressing Play in Song mode "lag like crazy". `songTimeline.svelte.ts` and `patternStore.svelte.ts` are `.svelte.ts` (not plain `.ts`) specifically so their `placements`/`lengthSteps`/`effectiveLengths` fields can be `$derived` — Svelte's signal graph marks them dirty on the relevant `$state` write (`placementStore.placements`, `patternStore.patterns`, or any channel's `steps`/`notes`) and only actually re-runs the computation the next time one is *read* after going dirty; reading an up-to-date derived (the common case, every idle tick during playback) is just a cached-value return. This lazy-pull-on-read behavior works from a plain, non-reactive call site like `audioEngine`'s scheduler exactly the same as it would from a component template — no `$effect`/component context is needed to benefit from the caching, only to auto-*react* to it.
  - **Scheduling** — `audioEngine.tick()`'s old single per-channel loop body is now `scheduleChannelStep(ch, step, playTime, loopBound, barLength, loopNotes = true)`, called by both modes: pattern mode calls it once per `getChannels()` entry with `loopNotes` left at its default; song mode calls it once per active placement's `getPatternChannels(patternId)` entry, with `step` translated to be relative to that placement's own start, `loopBound` set to the *placement's own* (content-floored) `lengthSteps`, and `loopNotes = false`. `loopNotes` decides whether a note-based channel loops on its own content the same way `channelLoop.ts`'s `channelLoopLength()` already makes a step-based channel do (tiling to fill `loopBound` — pattern mode's existing "per-channel independent looping" behavior, unchanged): true (pattern mode) loops both notes and steps identically; false (song mode) only loops step-based channels — a note-based (piano-roll) channel instead uses the placement's full `loopBound` as its own loop length, i.e. it just plays through once and goes silent for any remainder, since `getSongPlacements()` already sizes the block to the *longest* channel's content, so a shorter note channel "looping" there would read as an unwanted extra repeat rather than the drum-style "tile the loop" a step channel wants. Several placements (different tracks) can be simultaneously active at the same absolute step. A `kind: 'clip'` placement isn't step-sequenced — it fires once, as a plain one-shot via the existing private `scheduleHit()`, the instant its region begins (`localStep === 0`), center-panned straight to Master (a clip has no channel/mixer-track identity of its own), and rings out to its own natural length.
  - **Stop-at-end, not loop** — pattern mode still loops forever (unchanged). Song mode plays the arrangement once: when `tick()`'s song-mode branch increments `scheduledStep` past `getSongLength()`, it clears `timerId` and calls the `onSongEnd()` callback (wired by `playbackStore` to `() => { this.isPlaying = false; }`) instead of wrapping back to 0 — the same end state as pressing Stop. Whatever was already scheduled for that final step still rings out naturally; only *future* scheduling stops. `getPosition()` branches the same `loopBound` source (`getSongLength()` vs `getActiveLength()`) for the visual playhead, unaffected by the stop-at-end change since `playbackStore`'s rAF loop stops calling it once `isPlaying` flips false.
  - **Soloing a channel** (Piano Roll's own play button) and per-channel step-button highlighting have no meaning against song mode's placement-based scheduling — `PianoRoll.svelte`'s `handleTogglePlay()` and `ChannelRack.svelte`'s own play button both force `transportMode = 'pattern'` before starting playback (mirrors each other). `PianoRoll`'s continuous playhead line (`wrappedStepFraction`) is likewise only shown in pattern mode, gated alongside its existing `isPlaying` check.
- **Visual sync** — the `requestAnimationFrame` loop owned by `playbackStore` (see above) calls `audioEngine.getPosition()` every frame to determine the display step, both floored (`currentStep`) and continuous (`currentStepFraction`). This matches what's audibly playing, not what's been pre-scheduled.
- **Loop-position wrap-around, made resilient to a changing `activeLength`** — both `audioEngine.tick()`'s scheduling and `getPosition()`'s visual-clock math need "how far into the loop are we" (`someGrowingCounter % activeLength`), but `activeLength` isn't constant — it grows whenever the Piano Roll's auto-extend effect adds a bar mid-playback (see "Auto-extend" under "Piano Roll"). Naively taking `%` of an ever-growing counter (raw elapsed audio time, or an unbounded `scheduledStep`) against a divisor that just changed jumps to a wherever-unrelated remainder instead of continuing smoothly. Both are fixed the same way: keep the counter itself bounded to `[0, activeLength)` as you go, re-wrapping only by exactly one full cycle at a time using whatever `activeLength` is *current* at each wrap — `scheduledStep` is wrapped immediately after each increment (`this.scheduledStep = (this.scheduledStep + 1) % activeLength`) rather than left to grow unbounded; `getPosition()`'s `loopAnchorTime` (the audio-context time the current loop cycle began) is advanced forward by exactly one cycle's worth of seconds each time real elapsed time crosses one, re-reading `activeLength` on each advance. A value that's already `< activeLength` naturally survives `activeLength` growing (mod against a larger number is a no-op), so no jump.
- **Solo playback (Piano Roll audition)** — when `playback.soloChannelId` is set, the `getChannels` closure passed to `audioEngine.start()` filters to just that one channel instead of returning `channelStore.channels`. There is still only ever one `playback.isPlaying`/one running `audioEngine` instance — solo is just a filter, not a second engine. `ChannelRack`'s and `Toolbar`'s play/stop always clear `soloChannelId` (full-pattern playback); only the Piano Roll's own play button sets it (see "Piano Roll" below).
- **Channel Rack solo (`ChannelData.soloed`)** — a completely separate mechanism from `playback.soloChannelId` above: Ctrl+click a channel's `.mute-dot` in `ChannelRow.svelte` (`toggleMuteOrSolo()`, delegating to `channelStore.toggleSolo(id)`) to toggle `channel.soloed` instead of `channel.muted` (a plain click still toggles mute as before). **Single-solo, not multi-solo** — unlike the Mixer's own `soloed`, at most one Channel Rack channel can be soloed at a time: `toggleSolo(id)` clears every other channel's `soloed` before setting `id`'s, so soloing a different channel un-solos whichever one was previously soloed; Ctrl+clicking the already-soloed channel again just clears it, leaving nothing soloed (the "reverse"). Audibility itself still mirrors the Mixer's `isAudible()` formula (`channelStore.anySoloed`/`channelStore.isChannelAudible(ch)`: an explicit mute always wins regardless of solo) — only the "how many can be soloed" rule differs; this remains a wholly independent field/mechanism scoped to the Channel Rack only, unrelated to `MixerChannelData.soloed`. Persisted the same way as `channel.muted` (part of `ChannelSettingsExport`/Rust's `ChannelSettings`, `#[serde(default)]` for `.alp` files saved before this field existed) — unlike the Mixer's own mute/solo, which stay ephemeral. Applies uniformly in both pattern and song mode (mirroring how `muted` already does): `audioEngine.ts`'s `scheduleChannelStep()` takes an `anySoloed` flag (computed once per `tick()` from a `getAnySoloed` closure threaded through `start()`/`startSong()`, the same live-getter convention as `getBpm`/`getChannels`/`getBarLength` — `audioEngine.ts` deliberately never imports `channelStore` itself) and skips a channel if `anySoloed && !ch.soloed`, checked alongside the existing `ch.muted` skip. Visually, a soloed channel's mute dot gets a glowing accent-color ring (`box-shadow`) rather than a color swap, layered on top of whatever fill mute already gives it (including the muted+soloed combination, which still reads as silent) — the app has only one accent color token, so this is a shape/glow distinction rather than a second color, similar reasoning to the Mixer's mute-circle/solo-square split.
- **Sample loading** — `audioEngine.loadSample(relativePath)` calls `invoke('read_audio_bytes', { relativePath })` and decodes with `decodeAudioData`. Results are cached in a `Map` keyed by relative path.
- **Preloading** — `audioEngine.warmUp()` (constructs the `AudioContext` without resuming it — construction never needs a user gesture, only `.resume()` does) and `audioEngine.preloadChannel(ch)`/`preloadChannels(channels)` (fire-and-forget `loadSample`/`resolveFolder` calls that piggyback on the existing dedup caches, so they never duplicate an in-flight or already-cached load) are called from `+page.svelte`'s `openProject` right after project state loads, and from `ChannelRack`'s sample-drop handler right after a channel's `samplePath`/`sampleFolder` is set. This exists because `scheduleHit()`'s staleness guard (see next bullet) used to silently drop a channel's very first trigger while its sample was still cold-loading — placing a note in the Piano Roll (or pressing Play right after opening a project) would produce no sound the first time, only on a second trigger once the buffer was cached.
- **Scheduling staleness cutoff** — `scheduleHit()` drops a hit if `loadSample()` resolves more than `STALE_CUTOFF_SEC` (150ms, widened from an earlier too-tight 50ms) after its intended `playTime`, to avoid an audible pile-up of stale beats. `triggerPitched`/`scheduleHit` take an `allowLate` flag that bypasses this entirely; `previewNote()` (Piano Roll note audition — click/place/move) passes `allowLate = true` since a one-shot audition has no pile-up concern, while `tick()`'s scheduled playback keeps the cutoff enforced.
- **Step convention** — 16 steps = 1 bar of 4/4; each step = 1 sixteenth note. Step duration = `60 / BPM / 4` seconds. Color groups in ChannelRow (4 steps per group) correspond to one beat each.
- **Metronome** — Toolbar's metronome button (`Toolbar.svelte`'s `toggleMetronome()`) toggles `playback.metronomeOn` (see above) and, only on the on-transition and only if playback isn't already running, also calls the same `play()` the real Play button uses — so enabling it is heard immediately instead of silently arming; turning it back off does not stop playback. `metronomeOn` is read inside `audioEngine.tick()` via a `getMetronomeOn` closure (threaded through `start()` alongside `getBpm`/`getChannels`/`getBarLength`, same live-value convention as those — toggling it mid-playback takes effect on the very next scheduled step, no restart needed). One click per quarter note (`step % 4 === 0`, the fixed steps-per-beat convention above), accented on beat 1 of every bar (`step % barLength === 0`, so it's correct for any time signature, not hardcoded to 4/4) via `scheduleMetronomeClick(accent, playTime)`: two short pre-recorded samples shipped under `data/samples/misc/` (`metronome02.ogg` accent, `metronome01.ogg` regular click) rather than a synthesized `OscillatorNode` tone, so the click reuses the exact same `loadSample()`/`playSample()` pipeline (caching, de-click ramps, the same `STALE_CUTOFF_SEC` staleness guard as `scheduleHit()`) as every other sample in the app instead of a one-off second sound path. Always plays center-panned straight to Master (`playSample(..., MASTER_TRACK_ID, ...)`) — it has no channel/mixer-track identity of its own, so it bypasses per-channel mixer routing entirely. `audioEngine.preloadMetronome()` (called once from `+page.svelte`'s `openProject`, alongside `preloadChannels()`) warms both samples into the cache ahead of time so toggling the metronome on right before pressing play doesn't cost a cold IPC+decode round trip on the very first click.
- **Sample paths** — `FileExplorer` dispatches a `FileDropDetail` (`types.ts`) in the `filedrop` event: `{ kind: 'file', path }` for a leaf, or `{ kind: 'folder', path, files }` (immediate child file paths, non-recursive) for a directory. `ChannelRack`'s drop handler sets `channel.samplePath`/`channel.sampleFolder` (mutually exclusive — setting one clears the other) accordingly.
  - **quick-xml round-trips `Option::None` as `Some("")`, not `None`** — `src-tauri/src/project.rs`'s `sample_path`/`sample_folder` are `Option<String>`; quick-xml serializes `None` as an empty self-closing tag (e.g. `<samplePath/>`) and deserializes that back as `Some("")` rather than `None` (verified directly against the installed quick-xml version — this isn't fixable by `#[serde(default)]`, which only covers a *missing* tag, not an *empty* one). `channelStore.importState()` (`channelStore.svelte.ts`) normalizes this with `c.samplePath || null` / `c.sampleFolder || null` (`||`, not `??` — `??` only falls through on `null`/`undefined`, not `""`). This matters because `formatChannelLabel` (`sampleName.ts`) does `channel.sampleFolder ?? channel.samplePath`, so a stray `""` left in the unset field (which `??` treats as "set") silently wins over the real path and shows "Drop sample" even though the sample is still assigned and still plays — normalize at the one import boundary rather than patching every consumer.
- **Notes vs. steps (dual scheduling path)** — each `ChannelData` has both a flat `steps: boolean[]` (step sequencer) and a `notes: Note[]` (piano roll). In `audioEngine.tick()`, a channel with any `notes` plays *only* from that note data (pitched via `playbackRate`, scaled by `note.velocity`); a channel with an empty `notes` array falls back to the original boolean-step behavior unchanged (played at pitch 60, i.e. unshifted for a single-sample channel). This means drawing in the Piano Roll fully supersedes that channel's step-sequencer row — the two are not merged/overlaid. Both paths funnel through `audioEngine`'s private `triggerPitched(ch, targetPitch, ...)`, which is what actually branches on `samplePath` vs `sampleFolder`.
- **Pitch → playback rate** — `2 ** ((note.pitch - 60) / 12)`, i.e. MIDI-style semitone pitch with `60` as the unshifted (rate = 1) reference, using the octave-numbering convention where `60 = C5` (see `pianoroll/pitch.ts`'s `pitchName`). There is no MIDI file import/export, so this convention only needs to be internally self-consistent. For a multisample channel (`sampleFolder` set) the reference pitch is whichever recorded sample is closest to the note being played, not always 60 — see below.
- **Channel volume goes up to 200%** — `channel.volume` (bound to `ChannelRow`'s Volume `Dial`, see "Dial.svelte" above) ranges `[0, 2]`, not `[0, 1]`; `audioEngine.ts`'s `playSample()` clamps `vol` to `[0, 2]` accordingly (was hard-clamped to `1` before, which would have silently capped any boost back to unity). The master `DynamicsCompressor` (see `ensureCtx()`) is what keeps a boosted channel at high velocity from clipping, not the volume clamp itself.
- **ADSR envelope on piano-roll notes** — `audioEngine.ts`'s `playSample()` applies a fixed attack/decay/sustain/release envelope (constants `ATTACK`/`DECAY`/`SUSTAIN`/`RELEASE` near the top of the file — `ATTACK` is `0` since samples already carry their own natural attack, so this only shapes decay/sustain/release) and an explicit `src.stop()`, scaled to fit within the note's own length in seconds (`note.length * stepDuration`, passed down as `durationSeconds` through `triggerPitched`/`scheduleHit`/`playSample`) — this is what makes a note actually stop when its length says it should instead of ringing out to the sample's full recorded duration. Envelope stage lengths are clamped to fit inside very short notes so a 1-step note doesn't produce a broken/negative envelope. Plain step-sequencer one-shots (`ch.steps[step]`, no note data, `durationSeconds` left `undefined`) keep the old behavior — ring out to the sample's own end with just a de-click ramp — since a "length" concept doesn't apply to them and cutting them short would regress drum-style hits. The ADSR values are fixed for now (no per-channel/UI controls yet).
- **`patternLength` vs. `activeLength`** — `channelStore.patternLength` is the *editable canvas size*: it's what `PianoRoll`'s auto-extend effect grows by one bar at a time to give the user room to keep drawing (see "Piano Roll"), and it's what the Piano Roll's own grid/ruler/overview are sized against for editing. `channelStore.activeLength` (a getter over a memoized `$derived`, `channelStore.svelte.ts` — read by every ChannelRow and every scheduler tick, so it must not re-scan per read) is the *content-driven playback loop bound* used for scheduling: it bar-scans `patternLength` and only counts a bar if *any* channel has content there, so a freshly auto-extended trailing bar that's empty for every channel doesn't count until something is actually drawn into it. This distinction exists because a channel whose real content nearly fills the pattern (e.g. a 3-bar piano part that just triggered a 4th-bar auto-extend) must not be mistaken for a channel that's *genuinely* meant to loop short — see the next bullet.
- **Per-channel independent looping** — `channelStore.activeLength` (not `patternLength`) is the shared bound every channel loops within, but each channel loops on *its own* content length rather than all repeating together at that bound. `audioEngine.tick()` calls the shared `channelLoopLength(ch, activeLength, barLength)` (`src/lib/channelLoop.ts`, also used by `ChannelRow.svelte` — see below) for every channel on every scheduled step: it scans the channel's notes/steps bar-by-bar (`barLength` = `channelStore.barLength`, fetched live via a `getBarLength` closure passed into `audioEngine.start()`/`playbackStore`, same pattern as `getBpm`/`getChannels`) and finds the *last* bar containing any content; the loop length is that bar's end, rounded up — i.e. the point after which a full bar (`beatsPerBar` beats) has no notes. The absolute step (`scheduledStep`, already kept wrapped within `[0, activeLength)` — see "Loop-position wrap-around" above) is then taken modulo that channel's own loop length (`chStep`) before being matched against `note.start`/indexing `ch.steps`. Concretely: a channel with 16 beats of content inside a 32-beat active region plays its content twice instead of once followed by 16 beats of silence. A channel with no trailing empty-bar gap (content reaches the very end of `activeLength`) just plays through once, unchanged. Leading silence (content that starts after bar 0) is preserved correctly since the scan looks for the *last* occupied bar, not the first *empty* one.
- **Per-channel loop wrap in the UI (`ChannelRow.svelte`)** — `playback.currentStep` is a single absolute step shared by every channel, but `ChannelRow`'s 16 fixed step buttons (and its `MiniNoteRoll` preview for note-based channels) only make sense modulo that specific channel's own loop length. `ChannelRow` computes `chLoopLength = channelLoopLength(channel, channelStore.activeLength, channelStore.barLength)` and `wrappedStep = activeStep % chLoopLength`, and uses `wrappedStep`/`chLoopLength` (not the raw `activeStep`/`channelStore.patternLength`) for both the step-button highlight and the `MiniNoteRoll` props — otherwise a short-looping channel's highlight (or preview width) would only be correct during the pattern's first cycle. `PianoRoll.svelte`'s own grid/ruler/overview intentionally keep using the full `channelStore.patternLength`, since those represent the editable canvas, not a fixed-size loop preview.

## Toolbar audio monitor & peak meter

`audioEngine.ts`'s `buildCtx()` taps the master bus (post-compressor, pre-destination) with pure analysis nodes that never connect onward themselves, so adding/removing them can't affect what's actually audible: one `AnalyserNode` (`fftSize = 2048`) sees the full mixed-down signal, and a `ChannelSplitterNode` feeds two more single-channel `AnalyserNode`s (`fftSize = 1024`) for independent left/right taps. Exposed as `getAnalyser()` / `getStereoAnalysers()` — both return `null` until the `AudioContext` exists (before `warmUp()`/`ensureCtx()` ever runs).

- **`BlackBox.svelte`** — the toolbar's dark monitor rectangle, now a `<canvas>` wrapped in a `<button>`. Click toggles `mode` between `'wave'` (oscilloscope, `getByteTimeDomainData`) and `'spectrum'` (`getByteFrequencyData`, grouped into `BAR_COUNT` bars via an exponential bin-edge mapping — `bins ** (bar / BAR_COUNT)` — so low frequencies, where most musical energy sits, aren't crushed into the first pixel or two of a linear bin→pixel map).
  - **Both modes autoscale** so quiet passages stay visible and loud ones never clip off-canvas: each frame computes its own peak (max deviation for the wave, max bin value for the spectrum), folds it into a running gain ceiling (`waveGain`/`freqGain`) with fast attack (a louder frame instantly claims the new ceiling) and slow per-frame decay (`WAVE_RELEASE`/`FREQ_RELEASE = 0.965`, roughly a 1-second falloff) — the same attack/release shape as `PeakMeter`'s smoothing, just applied to a display *scale* instead of a displayed *level*. Everything that frame is drawn relative to that ceiling, so the loudest sample/bin lands exactly at the edge. Each has a floor (`WAVE_GAIN_FLOOR = 0.04`, `FREQ_GAIN_FLOOR = 24`/255) so near-silence settles the ceiling at a fixed minimum instead of amplifying noise into full-scale jitter (moot in practice — true digital silence is an exact constant in the byte buffer, not noise, so it just draws flat/empty).
- **System audio source** — with Preferences › General › "Audio monitor source" = System audio, BlackBox reads `systemAudio.getAnalyser()` instead (the peak meter stays app-only). `capture.rs` records the default sink's PulseAudio/PipeWire **monitor** (everything the computer plays, this app included — harmless since it's never played back) at the AudioContext's own rate (Pulse resamples) and sends mono f32 chunks over a binary `tauri::ipc::Channel`. `systemAudio.ts` posts them to an inline (Blob-URL) `AudioWorklet` ring buffer (drops the oldest past ~4096 samples so the display can't lag, outputs silence when dry) → its own `AnalyserNode` → zero-gain → destination (the graph must reach the destination to be pulled). BlackBox starts/stops capture in an `$effect` on the pref, so it only runs in the project view; `onContextRebuilt` restarts it at the new rate. In system mode the rAF loop runs whenever that source is selected, not just while the transport plays. WebKitGTK has no usable `getUserMedia` for monitor sources, hence the Rust capture.
- **`PeakMeter.svelte`** — the two horizontal bars, one per stereo channel, read from `getStereoAnalysers()`.
  - **dB-scaled, not linear** — raw peak (`max(|byte - 128| / 128)`, attack/release-smoothed exactly as before) is converted via `20 * log10(amp)` and mapped from `[MIN_DB, 0]` (`MIN_DB = -48`) onto the bar's `[0, 1]` width (`ampToFraction()`). This is what makes "max" mean something: 0dBFS (true digital clipping) is the bar's actual right edge, and normal listening levels spread out across most of the bar's width instead of a linear scale bunching everything below roughly -20dB into the leftmost sliver.
  - **Fill color reddens near the top, not linearly** — `colorForLevel()` stays green below 75% of the dB-mapped range, blends green→yellow from 75–90%, then yellow→red from 90–100%, so a channel only visibly warns once it's actually closing in on 0dBFS rather than tinting yellow/red for perfectly ordinary levels.
  - **5-second peak-hold line** — a thin vertical marker (`.tb-peak-hold`) per bar shows the highest dB-mapped level reached in the trailing `HOLD_WINDOW_MS = 5000`ms, independent of the bar's own attack/release decay. Implemented as a small `{t, level}` ring buffer (`historyL`/`historyR`) pruned to the window each frame — simple, exact, and cheap at ≤300 entries/channel (5s × 60fps) rather than an approximated single-value hold-and-decay.
- **Both components gate their `requestAnimationFrame` loop on `playback.isPlaying`**, mirroring `playbackStore`'s own `#startRaf`/`#stopRaf` convention — idle (stopped) rendering is a single static draw (flat line / zeroed bars), not a continuously running loop with nothing to show. Stopping also drops all autoscale/hold state (`waveGain`/`freqGain` reset to their floors, `historyL`/`historyR` cleared) so the next playback starts scaled fresh rather than carrying over a stale ceiling from before. Neither component reacts to one-off previews (`audioEngine.previewNote()`, e.g. auditioning a Piano Roll note while stopped) — visualization is tied to transport state, not to any sound actually being scheduled.

## Dropping samples into the Channel Rack to create channels

Dragging a file/folder from `FileExplorer` and dropping it anywhere in the Channel Rack's channel list (not onto an existing channel's own sample-name box, which keeps its original meaning of reassigning that channel's sample) creates a **new** channel with that sample/folder, inserted at the dropped position rather than always appended at the end — first, last, or anywhere in between, mirroring where the cursor was released. A thin glowing insertion line (`.insert-line`, `ChannelRack.svelte`) tracks the drop position live while dragging, snapping to whichever side of the nearest row's vertical midpoint the cursor is on.

- **`FileExplorer.svelte`'s `filedragover` event** — a new custom event, dispatched on the current hover target on *every* pointermove tick during a drag (unlike `filedragenter`/`filedragleave`, which only fire once when the hovered target itself changes), carrying `{ x, y }` (`FileDragOverDetail`, `types.ts`). This is what lets `ChannelRack.svelte` track live cursor position for the insertion line without standing up a second document-wide `pointermove` listener of its own — FileExplorer already runs one for its own drag tracking (see the Playlist's "Do not reintroduce a second always-on document-wide pointermove listener" note above; the same reasoning applies here), so this just rides on it.
- **`ChannelRack.svelte`** makes `.rack-list` itself a `data-sample-drop` target (`rackListEl`). Because `elementsFromPoint` (`FileExplorer.svelte`'s drop-target resolution) always finds the innermost matching element first, a row's own `.sample-drop` box still wins whenever the cursor is directly over it — so hovering elsewhere in a row (or below the last row, or above the first) resolves to `.rack-list` instead and drives the insert-new-channel path. `computeInsertIndex(clientY)` walks the list's direct `.ch-row` children (queried fresh each call via `:scope > .ch-row`, not `.children`, since the insertion-line `<div>` itself is also a direct child while shown) and returns the index of the first row whose vertical midpoint is below the cursor (or the row count, to insert last). `insertLineTop(index)` converts that boundary into a scroll-aware local offset for the line's `top` style.
- **`channelStore.addChannel(atIndex?)`** now accepts an optional insertion index (splicing instead of pushing) and returns the created channel, so `ChannelRack`'s drop handler can set `samplePath`/`sampleFolder` on it immediately and call `audioEngine.preloadChannel()` — the same two steps `onSampleDrop` already does for the existing per-row assign case. The footer's `+` button still calls `addChannel()` with no index, appending as before.

## Channel Rack row context menu

Right-clicking a `ChannelRow` (anywhere except the step buttons, which keep their own right-click-to-erase-step meaning) — including the sample field, which used to have its own separate plugin menu — opens `ChannelRowMenu.svelte`, portalled onto `<body>` the same way as `DragTooltip.svelte`. A local `menuView: 'main' | 'rename' | 'recolor' | 'midi'` lets Rename/Recolor/MIDI out take over the same menu body instead of opening a second portal:

```
PLUGINS          (every registry plugin, assigned one ✓ — picking assigns + opens it)
Remove plugin    (only when one is assigned)
─────────
Fill every 2 steps
Fill every 4 steps
Fill every 8 steps
─────────
Rename
Recolor
Recolor randomly
─────────
MIDI out…        (see "MIDI" — ChannelMidiOutMenu.svelte)
─────────
Delete channel
```

- **Fill every N steps** — `fillEvery(n)` sets `channel.steps = channel.steps.map((_, i) => i % n === 0)`, i.e. every Nth of the channel's step buttons goes on and every other one is cleared. Scoped to the row's own `steps` array at whatever length it currently is (`channelStore.stepCount`, see "Growing the step sequencer" below) — not `patternLength`-aware, since the two are independent concepts (though `addSteps()` does keep `patternLength` caught up so newly added steps are actually playable).
- **Rename** — swaps the menu body for a single `<input>` seeded from `channel.name ?? formatChannelLabel(channel)`. Enter commits (`channel.name = trimmed || null` — an empty commit clears the override back to the auto-derived sample label); Escape or clicking the backdrop cancels without committing. Deliberately **no commit-on-blur** here (unlike `MixerChannelStrip.svelte`'s rename) — removing a focused input from the DOM can itself dispatch a trailing `blur`, which would re-commit a just-cancelled edit (the exact trap `MixerChannelStrip`'s `renameCancelled` guard exists for); simplest to just not wire blur at all for this short-lived widget instead of replicating that guard.
- **Recolor** — swaps the menu body for a `ColorWheel.svelte`, live-writing `channel.color` on every drag (same instant-apply convention as every other control in the app — Dial/Slider/ScrollField all write their bound value immediately too). `openRecolor()` seeds `channel.color = '#e6b07f'` first if it was `null`, since `ColorWheel` takes a plain non-null hex `value`.
- **Recolor randomly** — `channel.color = randomColorfulHex()` (`colorUtils.ts`), one click, closes immediately like Delete.
- **Coloring is scoped to the sample-name box only, not the whole row** — `ChannelRow.svelte`'s `.sample-drop` div gets an inline `background: ${channel.color}` when set; nothing else in the row changes. `dropTextColor` (`$derived.by`, luminance check `(r*299+g*587+b*114)/1000 < 140`) switches the sample-name text between light/dark so it stays legible against an arbitrary user-picked hue, since a custom color can't be assumed dark the way the app's own palette is.
- **`ChannelData.name`/`ChannelData.color`** (`types.ts`) are both `string | null`, following the exact `samplePath`/`sampleFolder` null-until-set convention: `null` means "no override" (label auto-derives from the sample, box uses default styling). Persisted the same way as `samplePath`/`sampleFolder` — `ChannelSettings` on the Rust side (`project.rs`) has matching `Option<String>` fields with `#[serde(default)]`, and `channelStore.importState()` normalizes with `c.name || null`/`c.color || null` for the same quick-xml `Option::None → Some("")` reason documented under "Sample paths" below.

## Growing the step sequencer

`channelStore.stepCount` (default 16) is how many step buttons every channel's `steps` array has — a single global number shared by every channel *and* every pattern (same "one number, not per-pattern" convention as `beatsPerBar`/`patternLength`; only the per-pattern step/note *content* is per-pattern-scoped). Growing it, via `channelStore.addSteps(beats)`, appends `false` to every channel's live `steps` array plus every pattern's stashed content in `#patternContent` — so the rack stays the same width no matter which pattern is open — and also bumps `patternLength` up (snapped to a whole bar, same rule as its own setter) if `stepCount` would otherwise exceed it. That last part matters: `patternLength` is what bounds `activeLength`'s bar-occupancy scan, which every channel's own loop length (`channelLoop.ts`'s `channelLoopLength`) is computed against — a step beyond `patternLength` is never scanned into either, so without this a newly added step could be painted on but would silently never play. `ChannelRack.svelte`'s rack-level right-click menu (distinct from `ChannelRow`'s own per-row fill/rename/recolor/delete menu — guarded by `(e.target as HTMLElement).closest('.ch-row')` so a right-click on an actual row still opens that row's menu, not this one) drives both directions:

- **"Add steps…"** — swaps the menu body for a single number input (same convention as `ChannelRow`'s Rename) — Enter commits `channelStore.addSteps(n)` where `n` is beats (groups of 4 steps), Escape/backdrop cancels. Also reachable by **dragging the Channel Rack window wider**: an `$effect` (deps: `rackListWidth` via `bind:clientWidth` on `.rack-list`, `nameColWidth` — deliberately *not* `channelStore.stepCount`, see "Trim steps" below for why) measures the live DOM trailing gap after the last step button of the first plain step-sequencer row it can find (`channelStore.channels.findIndex(c => c.notes.length === 0)` — a note-based row renders a `MiniNoteRoll` instead, sized completely differently, so it's skipped as unusable for measurement; if every channel has notes, nothing grows), same "query the live DOM" convention `computeInsertIndex`/`insertLineTop` already use elsewhere in this file. Whenever that gap fits a whole extra beat's worth of steps (4 × 26px, i.e. `.step`'s 24px width + `.steps`' 2px gap), it calls `addSteps()` for however many beats now fit in one shot. Shrinking the window never removes steps — `addSteps()` itself is additive-only, and a negative/zero fit is just a no-op.
- **"Trim steps"** — the inverse, `channelStore.trimSteps()`: a single-click action (no sub-view, same as `ChannelRow`'s "Recolor randomly"/"Delete channel"). Scans every channel's `steps` array in every pattern (live channels plus every stashed `#patternContent` entry — an unvisited pattern has no stash entry and so can't be holding any content either) for the single highest step index that's active *anywhere*, then trims every channel/pattern's `steps` array down to just past that index (rounded up to a whole beat, floored at one beat so it can never trim to nothing). **Only ever removes trailing steps, never from the middle** — a step that happens to be unused everywhere but sits before the highest-used index anywhere is left alone, since the array is still one shared length across every channel/pattern. Doesn't touch `patternLength` (unlike `addSteps()`, shrinking it back down isn't needed for correctness, and it may still be legitimately driven by note content past the trimmed step range). The auto-grow-on-resize effect above deliberately excludes `channelStore.stepCount` from its dependencies specifically so a trim isn't immediately undone by the window still having room — steps only come back once the window is *actually* dragged wider again.

## Multisample instrument folders

Dragging a **folder** (rather than a single file) from `FileExplorer` onto a channel's sample drop zone builds a simple multisample instrument instead of a one-shot: `channel.sampleFolder` is set (and `samplePath` cleared) instead of the other way around. This exists because many sample libraries ship each instrument as a folder of raw audio files, often with the recorded note baked into the filename (e.g. `Strings C1.wav`, `01_SAX_LONG G#1ogg.wav`); any accompanying proprietary preset files are ignored — only the raw audio files are used.

- **`src/lib/pianoroll/pitch.ts`'s `parseNoteName(filename)`** — regex-parses a trailing note token (e.g. `C1`, `G#3`, `A_2` — some libraries use `_` in place of `#` to keep filenames filesystem-safe) into a MIDI pitch using the same `60 = C5` convention as the rest of the app. Also strips a trailing `ogg` (case-insensitive, no separating dot) that shows up on some libraries' filenames — an artifact of the original `.ogg` extension being kept when the file was re-saved as `.wav`. Returns `null` when no note token is found (e.g. round-robin folders like `Guitar Pick (1).wav` or fully keymap-numbered ones like `Piano (1).wav` whose true per-key mapping isn't in the filenames).
- **`src/lib/multisample.ts`** — `buildMultisample(fileNames, folderPath)` parses every file in a dropped folder into a `MultisampleFolder`: `pitched` (files with a recognized note, sorted ascending) and `allPaths` (every file, for the fallback below). `pickFromFolder(folder, targetPitch)` resolves what to actually play: if `pitched` is non-empty, the nearest recorded pitch plus the `playbackRate` needed to reach `targetPitch` from it (this is the "if that note doesn't exist, create it from the nearest one" behavior); if `pitched` is empty, a random file from `allPaths` played at the same middle-C-relative rate a single-sample channel would use (i.e. round-robin/one-shot folders behave like today's single-sample channels, just with a random take per hit).
- **`audioEngine.ts`'s `resolveFolder(folderPath)`** — lazily lists a folder's contents via `invoke('list_dir_files', ...)` and runs `buildMultisample`, caching the result (same dedup-cache shape as `loadSample`'s `bufferCache`/`loadingPromises`) so the folder is only listed once regardless of how many notes/hits reference it.
- **Pattern-scoped step/note content** — channels (sample, mute, pan, volume, mixer track) are shared across all patterns, but each channel's `steps`/`notes` content is scoped per pattern. `channelStore.switchPattern(fromId, toId)` stashes the current `channels[i].steps`/`.notes` into a private `Map<patternId, Map<channelId, content>>`, then restores (or, the first time a pattern is visited, creates blank) content into the same channel objects — channel identity/order/settings never change. `patternStore`'s `selectedPatternId` is a getter/setter pair whose setter calls `channelStore.switchPattern` before updating, so switching patterns via the Toolbar dropdown, the Playlist patterns panel, or `addPattern()` all trigger the swap automatically; nothing else needs to call `switchPattern` directly.
